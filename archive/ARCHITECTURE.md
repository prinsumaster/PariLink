# PariLink Architecture Document

PariLink is a secure, real-time, AI-driven, horizontally scalable enterprise logistics platform. This document outlines the core architectural pillars, security boundaries, and data flow mechanisms that power the system.

## 1. Multi-Tenant Security & Isolation
Data isolation is the most critical constraint in PariLink's architecture. The platform employs a strict defense-in-depth approach to guarantee tenant isolation at multiple layers:

- **PostgreSQL Row-Level Security (RLS):** Every query executed against the database is gated by native PostgreSQL RLS policies.
- **Prisma Proxy Interceptors (GUC Injection Prevention):** To bridge the ORM with RLS, PariLink uses a custom `PrismaService.runAsTenant` implementation. This sets the PostgreSQL session variables (GUC) to the current `companyId`. Crucially, an interceptor sanitizes the input to prevent malicious GUC injection attacks.
- **Application-Level Strict Assertions:** Beyond the database layer, all service-level unit tests employ strict `expect.objectContaining({ where: expect.objectContaining({ companyId }) })` assertions to prove that no query can accidentally omit the tenant filter. This ensures that "vacuous tests" cannot hide isolation regressions.

## 2. Real-Time Data Flow (WebSockets & Pub/Sub)
The Intelligent Fleet Command Center streams live metrics to users via WebSockets, built on NestJS Gateways and Socket.io.

- **Strict Tenant Rooms:** In `CommandCenterGateway`, the initial handshake intercepts the user's JWT. If valid, the socket is forcibly placed into an isolated room named `tenant_${companyId}`. Global broadcasts (`server.emit`) are strictly forbidden; all events are scoped to these rooms.
- **Distributed Redis Backplane:** To support horizontal scaling across multiple server instances, the WebSocket layer integrates `@socket.io/redis-adapter` backed by `ioredis`. This Pub/Sub backplane ensures that an event emitted by Node A correctly reaches a socket connected to Node B, provided they belong to the same tenant room.

## 3. AI Dispatch Engine
The `DispatchAiService` leverages Google Gemini 2.5 (`@google/genai`) to generate optimal fleet assignments. 

- **Domain Serialization:** The engine extracts `PENDING` trips, `ACTIVE` vehicles, and `AVAILABLE` drivers, serializing the data into a highly constrained system prompt.
- **Structured Outputs (JSON Schema):** To bridge the semantic reasoning of the LLM with the rigid TypeScript domain, the AI SDK call enforces a strict JSON schema output. The AI is forced to return an array of assignments containing precisely the `tripId`, `vehicleId`, `driverId`, a `confidenceScore`, and its `reasoning`.

## 4. API Performance & Caching
Heavy financial aggregations (like the CEO Dashboard KPIs) are accelerated using a distributed Redis caching layer via `@nestjs/cache-manager`.

- **Tenant-Isolated Caching:** To prevent cross-tenant data leakage in the shared Redis instance, PariLink uses a custom `TenantCacheInterceptor`. This interceptor automatically intercepts the `@CacheKey()` decorator and appends `_tenant_${companyId}` to the key. This guarantees that Tenant A will never inadvertently serve a cached response generated by Tenant B.

## 5. CI/CD Quality Gates
Every Pull Request is gated by a rigorous GitHub Actions pipeline (`ci.yml`).

- **Database Initialization:** The pipeline provisions a PostgreSQL service container and automatically executes the raw SQL scripts to establish the secure `parilink_sys` user and roles, perfectly mirroring the production environment.
- **Mathematical Integrity Verification:** A standalone script (`verify-revenue.ts`) executes a raw SQL `SUM()` aggregation and compares it against the Prisma-generated application output. This mathematically proves that the RLS boundaries and application-layer status filters correctly constrain the live data, catching any ORM translation regressions before they reach production.
